# M6-T3: Assistant

Status: succeeded. Branch: `mobile/M6-T3`. Base: `mobile/native-app` @ `3acba7bc3`. Local commits only; no push.

## Delivered

- **Transport** (`src/features/assistant/transport.ts`, `chat.ts`): a port of web `chat.ts`. `useAssistantChat` runs `@ai-sdk/react` `useChat` over a custom `ChatTransport`:
  - `sendMessages` sends only the newest message to `streamClient.agent.messages.send`. It sends the context chips as they are at send time (a ref, not a closure) and the attachment IDs from `body`.
  - `reconnectToStream` uses `streamClient.agent.messages.resume`.
  - SSE strings are parsed with `parseJsonEventStream` and `uiMessageChunkSchema`. A malformed frame is dropped, and only its error name is logged.
  - `sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithToolCalls`, so answering a question continues the reply.
  - **Difference from web: `resumeStreamIsReplay: true`.** The server's resumable stream replays the reply from its start. Without the flag, resuming after a disconnect duplicated the text already received ("MostMost of your bullets"). The scenario harness caught this.
- **Resume / stop.**
  - Reopening a conversation with `activeRunId` resumes it, as on web.
  - On mobile, an `AppState` return to the foreground also resumes. If the stream errored (the OS cut the connection) and `threads.get` still reports an active run, the chat clears the error and resumes.
  - Stop calls `agent.messages.stop`, then `chat.stop()`, which aborts the request. The partial reply stays, followed by "Stopped. No edits were proposed. Continue".
  - Retry re-sends a failed continuation and regenerates anything else (web parity).
- **`ChatView`** (`src/features/assistant/chat-view.tsx`, the wave contract below). Ports web `Conversation` and `CoachThread`:
  - Lazy thread creation on the first message or the first attachment. An attachment-created draft thread is reused.
  - The thread is re-read when it opens. A brand-new thread skips the read.
  - Message log with auto-follow unless the user scrolled up, "Thinking…", the error card (Retry / Switch model), Copy transcript (`expo-clipboard`).
  - Composer: context chips, attachments, a box that grows to 6 lines, a 34 pt Send/Stop circle in a 44 pt target, and the privacy line. It sits in a `react-native-keyboard-controller` `KeyboardAvoidingView`.
- **Message parts** (`messages.tsx`):
  - Markdown text with a streaming cursor.
  - Tool status lines (read resume/letter/attachment, web search, read page with the clipped and fallback notes, legacy patch).
  - Question card: choices, or "Or in your own words…" with Send.
  - Change sets, sources (public hosts only, the same rule as `agentWebSources`, parsed without `URL`), and "Saved a story".
  - Coach memory: "Remember this for future coaching?" with Remember (`career.saveFact`) or Not now, and "Remembered: … · Undo" (`career.forgetFact`).
- **Change sets → draft** (`proposals.ts`, `document.ts`):
  - Accept and Accept all call M3-T3 `useResumeStore.getState().update(recipe, { newStep: true })` with `applyProposal`. A toast offers Undo, which calls `store.undo()`.
  - Reject, accept and undo-to-pending go to `agent.messages.setEditStatus` (web parity).
  - Stale and locked states come from `getProposalState` on the draft data. `useResumeAssistantDocument` reads only from the draft store and opens or closes nothing.
- **Page markings** (`proposals.ts`, `page-marks.tsx`):
  - Proposals are published to a small zustand store keyed by resume ID. They stay there after the Assistant closes, so Page can mark pending edits (mockup "Page · proposed-edit markings").
  - `markProposals` is a port of web: old text struck through in grey, new text highlighted.
  - Starting a new conversation clears the markings.
- **Builder Assistant** (`assistant-screen.tsx`, route `app/builder/[id]/assistant.tsx`, full-screen modal):
  - Header: sparkle, Assistant, model chip → `ModelSheet`, New conversation, Past conversations, Close.
  - Past conversations are grouped "This document" / "Other documents · n", with outcome text and Delete behind a confirmation. Another resume's thread opens that resume's assistant on the thread. A letter thread opens the letter, because mobile has no letter assistant route.
  - Context chips: resume and "{company} posting", removable.
  - The disclosure line is web's. Suggestions are the default set or the Prepare set.
  - The locked state is disabled with an explanation.
  - "Opening the resume…" shows until the builder's draft owner has the resume.
- **Provider setup inline** (`provider.tsx` `ProviderGate`):
  - The server isn't set up (`PRECONDITION_FAILED`), connections failed to load (Retry), or loading.
  - No provider: "Connect an AI provider" opens M6-T4 `AIProviderSetupSheet` in place, and links to Settings. A successful test refreshes `useHasAIProvider`, and the chat appears.
  - A conversation whose connection was removed moves to the default (`useConversationConnection`).
- **Career Coach** (`coach-screen.tsx`, route `app/(tabs)/career/coach.tsx`) reuses `ChatView` with `document: null`:
  - Toggle chips: Applications, "Knowledge · n facts", Web research, and "n saved offers".
  - The privacy line names exactly what is sent. Sending is disabled while Knowledge is loading or has failed.
  - Starters, and a model row.
  - Conversations sheet: New, open, rename (inline field), delete (confirmation).
  - Facts and stories are refreshed after each reply.
- **M6-T1 handoff:** `offerIdsFrom(params.offers)` accepts one value, several values, or comma-joined values, and keeps at most 2. The offers chip starts on and is sent as `context.offerIds`. Nothing is sent until the user sends.
- Every UI string uses Lingui macros; extraction was not run. Colours, type, spacing and radii come from tokens. No dependencies, manifests, root layouts, M1 contracts, draft code or other builders' files were changed.

**Node APIs on Hermes.** In the `ai` chat path, the client uses `structuredClone`, `TextDecoderStream`/`TextEncoderStream`, `TransformStream` and `Symbol.asyncIterator`. Expo's winter runtime installs all of them, and Metro injects the web streams. `AbortSignal.any`/`timeout` and `crypto.subtle` appear only in `ai`'s model-call and tool-approval paths, which run on the server; the client chat never calls them. `URL` is not used for source links. No Hermes runtime binary is on this host (only `hermesc`), so the bundle compiled to Hermes bytecode but did not run on Hermes here.

**Scenario harness** (`reports/M6-T3/verify.mjs`). It drives the shipped `sendAgentMessage`/`resumeAgentStream` through the AI SDK's real `Chat` class (the class `useChat` wraps), with mocked oRPC event iterators that yield the server's SSE strings. Scenarios:

- send: newest message only; context read at send time; attachment IDs filtered; abort signal passed.
- SSE frames split across chunks, plus a malformed frame that is dropped without logging its content.
- Disconnect mid-reply, then resume. This failed with duplicated text before `resumeStreamIsReplay`.
- Resume with nothing running is a no-op.
- Stop aborts the request and keeps the partial reply.
- An `ask_user_question` answer continues the reply with the tool output.

Test-audit gate: transport regressions are silent (duplicated text, lost context, a stop that doesn't abort) and the web suites can't reach the mobile transport. The harness follows the M3-T3/M6-T4 manual-harness pattern. It adds no production seams and no Vitest suite.
