## Contract and implementation decisions

Coordinator approved this correction to the original synchronous subsetter brief:

```ts
renderSerializedDocWithLayout(doc: Record<string, unknown>): Promise<RenderWithLayoutResult>
subsetFont(bytes: Uint8Array, text: string): Promise<Uint8Array>
```

`FormeEngine.prepareFont` already permits Promises. The native adapter can await this subsetter directly; the synchronous browser `createFontPreparer` must not receive it. `packages/pdf` remains untouched.

The native module accepts serialized JSON, returns PDF bytes as `Uint8Array`, and parses returned layout/warnings JSON in its TypeScript adapter. Swift uses an explicit serial `DispatchQueue`; Kotlin `AsyncFunction` uses Expo's background modules queue. The installed Expo source confirms Swift `Data` and Kotlin `ByteArray` convert bidirectionally to JS `Uint8Array`. Both paths were exercised, including invalid-document and invalid-font Promise rejection.

The C ABI uses input byte spans and an owned `FormeResult` containing PDF, layout, warnings and error spans. Callers copy output and free the entire result exactly once with `forme_result_free`. UTF-8 passes as bytes across JNI, including CJK and non-ASCII resume text. Panics are caught before crossing C; allocation aborts remain unrecoverable.

Android's imported Rust library has no ELF SONAME. CMake explicitly links it by library name (`IMPORTED_NO_SONAME TRUE`), avoiding a runtime dependency on a relative build-directory path. `readelf` verifies the JNI library needs `libforme_native.so`, and the installed app successfully loads it. The three supported ABIs are explicit; obsolete Android x86 is excluded. Rust arm64 ELF LOAD segments align to `0x4000` (16 KiB); a 16 KiB emulator was not exercised by S1.

## Engine provenance and fixture capture

Read both npm `pkg-web/forme.d.ts` / wasm-bindgen glue and crates.io `forme-pdf 0.28.0` source. WASM's `src/wasm.rs::render_pdf_with_layout(json, options_json)` calls:

```rust
forme::render_json_with_layout_and_options(json, forme::RenderOptions::default())
```

It returns `(Vec<u8>, LayoutInfo, Vec<String>, u32)`; the WASM API discards the pass count. S1 uses this same entry point and default options, with native compilation and no WASM features/runtime. Keep npm and Cargo versions pinned and upgrade them together; equal version labels alone do not replace parity checks.

`capture.ts` runs the existing `renderResume` pipeline against the untouched `sampleResumeData` for Azurill, Pikachu and Onyx, resolving the sample picture from `apps/web/public`. It captures the final document passed into the engine, all fonts encoded as data URIs, and the Node WASM PDF/layout/warnings. Each fixture needed one engine pass. Font download failure is fatal through existing `assertPdfFonts`.

Both npm web and Node WASM binaries have SHA-256 `b3ebb088de38a57dc2a670b53ed4321129c6a67f5e92cf61531082929445eeb7`; recorded in `packages/forme-native/fixtures/manifest.json`. WASM is used only by Node tooling to generate reference outputs, never by the mobile renderer or subsetter. The mobile graph contains no runtime import of `@formepdf/core`; its import is type-only.

**The one JSON difference:** for `style.backgroundColor: None`, native `serde_json` emits `null`; WASM's `serde_wasm_bindgen` emits `undefined`, which disappears when JSON is saved. Geometry, text, source locations, child ordering, page metadata and non-null colors match exactly.

PDF.js prints `loca` / TrueType-function warnings on the original WASM PDFs too; these do not change text extraction and are distinct from Forme's empty warnings array. No raster/visual-equivalence claim beyond PDF byte identity is needed for these identical files.

It approximates incremental engine code, not an App Store archive. Android libraries depend on `libc++_shared.so`, already supplied by React Native; wrappers add a small amount beyond the table.

## Acceptance: font byte path and CJK subset

- [x] Evaluated pure-Rust subsetting; selected native HarfBuzz for fonts Forme can consume.
- [x] Subsetter timed ten times on each device, then its result rendered and extracted without text loss.
- [x] Byte-registration API and high-level limitation identified.

Typst `subsetter 0.2.6` explicitly removes `cmap` and other shaping information for already-shaped PDF glyph embedding. It is not a general-purpose input-font subsetter. S1 therefore links HarfBuzz `hb-subset`, preserving all OpenType layout features and the requested Unicode coverage, as the browser subsetter does. This decision comes from the crate's documented scope, not a claimed successful Rust-subsetter runtime probe.

SHA-256 `d45f67f0a7c0ca3f256950777ce6a61cc7ce5f9696d02900cbbaac25f8aa7d16`.

Text: `简历 经验 教育 技能 软件工程师 中文测试 你好世界 Reactive Resume 0123456789`.

| Platform | Input bytes | Output bytes | Reduction | Median of 10 ms |
| --- | ---: | ---: | ---: | ---: |
| iOS | 10,559,284 | 18,624 | 99.82% | 3.18 |
| Android | 10,559,284 | 18,624 | 99.82% | 9.90 |

Both platforms save the subset and a one-page PDF using it. The TypeScript adapter receives the subset as `Uint8Array` in `fonts[].src`, encodes it, and the native engine renders it with no warnings; PDF.js extraction matches all CJK and Latin characters after whitespace removal. The full font is a test fixture, not bundled into the renderer graph. Fonts' OFL notices are retained.

**Does the crate accept raw font bytes?** Its low-level registry does:

```rust
let mut context = forme::font::FontContext::new();
context.registry_mut().register("Noto Sans SC", 400, false, font_bytes);
// font_bytes: Vec<u8>
// LayoutEngine::layout(&document, &context) and PdfWriter::write(..., &context, ...) consume it.
```

But `render_json_with_layout_and_options` and `render_with_layout` create their own `FontContext` and decode `FontEntry.src: String` from base64/data URI. They expose no context or byte-injection parameter. Bypassing that top-level path would duplicate private validation, font registration and page-number-sentinel handling. S1 intentionally retains the proven entry point; the module encodes font byte sources to data URIs without mutating inputs. **No-base64 input is not available through the high-level 0.28.0 render API.** An upstream render-with-context/registered-font API would remove this cost later; it is not required to proceed with subsetting and caching.

## Recommendation for M3-T4 and native preview

Proceed with this engine design. These three representative templates prove native rendering, byte transport, font subsetting and parity on both platforms; no engine-level blocker to on-device native preview was found.

For M3-T4:

1. Run all 17 templates through the complete native adapter and shared repair pipeline on Hermes, rather than replaying only captured final JSON. Preserve all existing layout-repair and font-fallback behavior.
2. Reuse the page-count/per-page-text comparison and enumerate only the known optional-color serialization difference. Keep exact warnings/geometry checks; do not substitute blanket tolerances.
3. Inject the approved async subsetter via `prepareFont`, include the browser's generated punctuation/digits, and cache prepared subsets/data URIs by font bytes and character set. Persist downloaded fonts through the later injected file cache.
4. Pin npm and Cargo Forme together and rerun parity on every upgrade. The S1 module is tested on SDK 57; if integration chooses SDK 58, align module-core/peer dependencies and repeat the native gate there.
5. Test the PDF-page rasterizer and visible-page scheduler in their owning tasks, then profile the full edit-to-preview path on mid-range hardware. Neither those components nor physical-device performance are established by this engine spike.

Remaining limits are measured scope, not hidden fallbacks: base64 remains in the high-level engine JSON, native render currently cannot cancel a running Rust call, OOM is not recoverable, all-17-template parity and final store download sizes remain later gates. No WASM or WebView fallback was introduced.
