### Things M3-T1 must get right

1. **Send `resource=<server origin>` (RFC 8707) on both `/oauth2/authorize` and `/oauth2/token` (code and refresh grants).** Without it the server issues a 32-char **opaque** access token, and `/api/rpc` answers 401: `verifyOAuthToken` only verifies JWTs. With it, the access token is a JWT with `aud = [<origin>, <origin>/api/auth/oauth2/userinfo]`. `clientRegistrationDefaultResources` does not change this.
2. **Refresh single-flight.** Replaying an already-rotated refresh token (outside Better Auth's short reuse interval) makes the server delete the whole refresh family for that client and user (RFC 9700 §4.14). The newest refresh token then fails too (`400 invalid_grant`), and the phone is signed out. Two concurrent refreshes (for example, two screens hitting 401 at once) would do exactly this. Share one in-flight refresh promise. Already-issued JWT access tokens keep working until they expire (≤ 1 h), because they are self-contained.
3. **Redirect URI shape.** Better Auth validates private-use schemes per RFC 8252 §7.1: reverse-domain name, no authority. `rrspike://oauth/callback` is rejected (`invalid_redirect_uri`); `me.rxresu.spikes3:/oauth/callback` is accepted. This only matters if a custom scheme is ever used (see §3).
4. Better Auth answers `/oauth2/authorize` with JSON `{ url }` instead of a 302 when the request does not look like a browser navigation (no `Accept: text/html`) and a session cookie is present. Real browsers are unaffected; only scripted clients care.
5. Access tokens live 3600 s, refresh tokens 30 days (sliding: each rotation issues a fresh 30 days).

### DCR request body M3-T1 should send

```http
POST <registration_endpoint>          (from /.well-known/oauth-authorization-server)
Content-Type: application/json
```

```json
{
	"client_name": "Reactive Resume for iOS",
	"redirect_uris": ["https://<server-host>/auth/native-callback"],
	"token_endpoint_auth_method": "none",
	"grant_types": ["authorization_code", "refresh_token"],
	"response_types": ["code"],
	"application_type": "native",
	"scope": "openid profile email offline_access api:read api:write api:delete"
}
```

- `client_name`: "Reactive Resume for Android" on Android. It is shown on the consent page.
- Register once per server and cache `client_id` in SecureStore keyed by server origin. Re-register only if the token endpoint answers `invalid_client` (the client was deleted).
- Authorization request: `response_type=code`, `client_id`, `redirect_uri`, `scope` (as above), `state`, `code_challenge` (S256), `code_challenge_method=S256`, `resource=<server origin>`.
- Token request: `grant_type=authorization_code`, `code`, `redirect_uri`, `client_id`, `code_verifier`, `resource=<server origin>`. Refresh: `grant_type=refresh_token`, `refresh_token`, `client_id`, `resource=<server origin>`.
- The spike registered `me.rxresu.spikes3:/oauth/callback` instead of the https URI, against a local server running with `FLAG_ALLOW_UNSAFE_OAUTH_REDIRECT_URI=true` (§3). Everything else in the body is exactly what M3-T1 should send.
- `offline_access` is what makes the server issue a refresh token. `api:*` scopes make permissions explicit (least privilege); without them a grant gets full access anyway.

## 3. Https callback status

- **Not proven locally.** No tunnel tool is installed (`cloudflared` and `ngrok` are both missing), and the brief forbids signing up for one. Without a public https host there is no AASA or assetlinks fetch by Apple's CDN or Google's verifier, so Universal Links and App Links cannot be exercised.
- **What was proven instead:** the full flow with a private-use scheme redirect, `me.rxresu.spikes3:/oauth/callback`, on a local server with `FLAG_ALLOW_UNSAFE_OAUTH_REDIRECT_URI=true`. A loopback `http://127.0.0.1:<port>` redirect is accepted by the policy, but it cannot be used on a phone: `ASWebAuthenticationSession` and Custom Tabs cannot intercept it, and the app would have to run an HTTP listener.
- **iOS API.** `expo-web-browser` 58 already implements it. `ios/WebAuthSession.swift` uses `ASWebAuthenticationSession(url:callback: .https(host:path:))` on iOS 17.4+ when `openAuthSessionAsync(..., { preferUniversalLinks: true })` is passed and the redirect is https. `AuthRequest.promptAsync(discovery, { preferUniversalLinks: true })` forwards the option. **No native shim is needed on iOS.** The app needs the Associated Domains entitlement `webcredentials:<host>` (per Apple's `ASWebAuthenticationSession.Callback.https` documentation; not exercised here) and the server must serve the AASA file listing the app ID under `webcredentials` (SV1).
- **Android.** `expo-web-browser` uses Custom Tabs (`androidx.browser` 1.6.0), not the newer Auth Tab. An https redirect returns to the app only through a verified App Link: an `autoVerify` intent filter for `https://<host>/auth/native-callback` (Expo `android.intentFilters`) plus `/.well-known/assetlinks.json` (SV1). `openAuthSessionAsync` on Android resolves from the `Linking` event, so it should work once the App Link opens the app. Unproven: what happens when verification fails (the browser loads `/auth/native-callback`, which is why SV1's fallback page matters), and whether Chrome keeps the App Link hand-off inside a Custom Tab on every vendor browser.
- **Still unproven, needs a public https deployment (preview or staging) with SV1:**
  1. iOS `.https` callback completes on a device or simulator with the entitlement (simulator needs the `?mode=developer` AASA path or a real CDN-fetched AASA).
  2. Android App Link verification and hand-off from Custom Tabs.
  3. The fallback page when the app is not installed or the link is not verified.
  4. `isAllowedOAuthRedirectUri` accepts `https://<APP_URL host>/auth/native-callback` already (own origin), so DCR needs no server change for the server's own callback host. Self-hosted servers on a LAN IP still work because own origins are always allowed.

## 4. SV4: does a phone stay signed in?

**No.** A phone loses API access when the browser session that approved it ends, at most 7 days after sign-in, even though its refresh token is valid for 30 days and keeps refreshing.

Evidence, from `S3/protocol-run.txt`:

| Case                                                    | Original access token | Refresh grant | Refreshed access token                                     |
| ------------------------------------------------------- | --------------------- | ------------- | ---------------------------------------------------------- |
| Control                                                 | OK                    | 200           | OK                                                         |
| Browser session **expired** (`expires_at` set to past)  | 401                   | 200           | **401**: carries the same expired `sid`                    |
| Browser session **signed out** (session row deleted)    | 401                   | 200           | **401**: carries `sid: null`                               |

Why:

1. The access token's `sid` is the browser session that approved the grant (`createUserTokens` → `createJwtAccessToken({ sid: sessionId })`). The refresh row stores the same `session_id`.
2. The refresh grant (`handleRefreshTokenGrant`) never checks the session. It copies `refreshToken.sessionId` into the new tokens, so every refreshed access token carries the original `sid`.
3. `verifyOAuthToken` (`packages/auth/src/config.ts:63`) rejects any token whose `sid` names a session that is missing or expired, and rejects `sid: null` as "Invalid token session" because `typeof null !== "string"`.
4. Sign-out deletes the session row; the FK `oauth_refresh_token.session_id … on delete set null` nulls it, so later refreshes mint `sid: null` tokens.
5. The browser session lasts 7 days (Better Auth default `expiresIn`). It only slides when the browser itself uses it (`updateAge`), which the phone never does. With `ASWebAuthenticationSession` sharing Safari's cookies, signing out of rxresu.me in Safari, or "sign out other sessions", also kills the phone.

So the effective phone session is `min(7 days, until that browser signs out)`. Re-auth is usually silent while the browser session lives, but after expiry the user must sign in again.

**Proposed minimal server change (not implemented):** tokens from a grant that holds `offline_access` stop being bound to the browser session. Revocation still works through the consent check (already in `verifyOAuthToken`, and the `delete-consent` hook revokes refresh tokens) and through `/oauth2/revoke`.

```diff
--- a/packages/auth/src/config.ts
+++ b/packages/auth/src/config.ts
@@ export async function verifyOAuthToken(token: string): Promise<JWTPayload> {
-	if (payload.sid !== undefined) {
+	const scopes = typeof payload.scope === "string" ? payload.scope.split(/\s+/).filter(Boolean) : [];
+	// offline_access grants outlive the browser session that approved them (OIDC Core §11). They are
+	// cut off by consent revocation and refresh-token revocation instead.
+	if (payload.sid != null && !scopes.includes("offline_access")) {
 		if (typeof payload.sid !== "string") throw new APIError("UNAUTHORIZED", { message: "Invalid token session." });
 		…
 	}
 	…
-	const scopes = typeof payload.scope === "string" ? payload.scope.split(/\s+/).filter(Boolean) : [];
```

- With it, a phone stays signed in as long as it refreshes at least once every 30 days (refresh rotation slides the 30 days), until the user removes the app from connected apps or signs out in the app.
- MCP clients that request `offline_access` get the same lifetime. That matches what they asked for. Clients without `offline_access` keep today's session binding.
- `!= null` also fixes the `sid: null` case after sign-out.
- Alternative if the owner wants sign-out-everywhere to also end phone access: keep the check for expired sessions only (drop the deleted-session case), and add an explicit "sign out all devices" action that revokes refresh tokens. That is a larger change.
- Not verified by running it: the diff is a proposal; the spike made no server source changes.

## 5. SV5 matrix (bearer token, no cookie)

| Call                                       | Result                                                                    |
| ------------------------------------------ | ------------------------------------------------------------------------- |
| `POST /api/auth/update-user`               | 401 Unauthorized. Better Auth endpoints use cookies only.                 |
| `GET /api/auth/api-key/list`               | 401 Unauthorized.                                                         |
| `GET /api/auth/get-session`                | 200 `null`.                                                               |
| oRPC `auth.exportData`                     | **OK.**                                                                   |
| oRPC `auth.createApiKey`                   | **403 FORBIDDEN** "Create API keys in your browser settings."             |
| oRPC `auth.deleteAccount`                  | **403 FORBIDDEN** "Account deletion must be performed in your browser settings." |

The brief and README §1.6 SV5 assume `createApiKey` and `deleteAccount` accept a bearer token. They do not: both check `context.authentication?.method !== "session"` on purpose (`packages/api/src/features/auth/router.ts`; the OpenAPI text says "keys and OAuth tokens cannot create credentials" / "cannot delete accounts"). The owner decision "API keys and account deletion are native" therefore needs a decision, not just wrappers:

- Option A: allow `method === "bearer"` (not `apiKey`) with `api:write` / `api:delete` for these two procedures. Smallest change. It means any OAuth client with `api:delete`, including MCP clients, could delete the account; restrict it to `application_type === "native"` clients if that matters (needs the client row, which `verifyOAuthToken` already loads).
- Option B: keep them browser-only and open the web settings page in the in-app browser tab, like the security screens.

`SV5` wrappers for `updateProfile`, `apiKeys.list` and `apiKeys.delete` are still needed as planned.

## 6. `resume.verifyPassword` for a bearer client

- `verifyPassword` is public. It returns `true` and grants access only through `Set-Cookie: resume_access_<resumeId>=<expires>.<hmac>; HttpOnly; Max-Age=600`.
- With a bearer token and no cookie, `getBySlug` stays `401 NEED_PASSWORD` after a successful verify. The bearer token does not help: `hasResumeAccess` reads only the cookie.
- Sending the returned cookie back works (`getBySlug` OK).
- **On device it works without any app code:** `expo/fetch` uses the platform cookie store on both iOS and Android, so the `resume_access_<id>` cookie set by `verifyPassword` is replayed on the next `getBySlug` and access is granted (`401 NEED_PASSWORD` → `200 true` → `200`), alongside the bearer token.
- Caveats for M7: the cookie lives in the shared native cookie store for 10 minutes, for every request to that server from the app, and is not in SecureStore. That matches the web behaviour and the data is the viewer's own unlock, so no change is needed. If the app ever clears cookies on sign-out, password unlocks go with them. A cookie-free option (return the signed value in the body and accept it in an `x-resume-access` header) is only worth doing if a non-cookie client needs it.
